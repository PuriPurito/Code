# Инструкция: report_non_std_objects

Настраиваемый отчёт выявляет объекты системы, которые были созданы вручную или изменены по сравнению с коробочной поставкой. Используется для аудита кастомизаций перед обновлением или передачей системы.

---

## Столбцы отчёта

| Столбец | Описание |
|---|---|
| ID | Идентификатор объекта |
| Название | Поле `name` объекта |
| Тип (каталог) | Имя каталога, например `remote_actions` |
| Коробочный | `Да` / `Нет` |
| Дата создания | Из `doc_info.creation.date` |
| Кто создал | Из `doc_info.creation.user_login` |
| Дата изменения | Из `doc_info.modification.date` |
| Кто изменил | Из `doc_info.modification.user_login` |

Столбцы генерируются один раз (см. `bGenerateColumns` ниже).

---

## Логика включения объекта в отчёт

Отчёт обходит три группы каталогов:

### Проход 1 — каталоги с полем `is_std`
Объект попадает в отчёт если выполняется **хотя бы одно** из условий:
- `is_std = false` или поле отсутствует
- `is_std = true` **и** `changed = true` (коробочный, но изменённый)

Дополнительно применяются фильтры по дате и логину (см. ниже).

### Проход 2 — каталоги без поля `is_std`
Попадают объекты, у которых в `custom_elems` нет `is_from_integration = true`.
Применяются фильтры по дате и логину.

### Проход 3 — динамические каталоги `doc_types`
Обрабатываются только каталоги, явно перечисленные в `aDocTypeCodes`.
Нет полей `is_std` / `changed` — применяются только фильтры по дате и логину.

## Параметры настройки (начало файла)

### `sMinModDate`
```javascript
var sMinModDate = "2024-01-01";  // формат YYYY-MM-DD
```
Минимальная дата изменения (включительно). Объекты с `modification_date` раньше этой даты, а также с пустой датой или пустым логином изменения — пропускаются.

---

### `bGenerateColumns`
```javascript
var bGenerateColumns = false;
```
Управляет разовой генерацией столбцов отчёта.

- Установить `true` → запустить отчёт → столбцы сгенерируются и сохранятся в документе отчёта.
- Вернуть `false` → при последующих запусках столбцы не пересоздаются.

---

### `aCatExclude` — исключённые каталоги
```javascript
var aCatExclude = [
    "collaborators",
    "learnings",
    // ...
];
```
Каталоги из этого массива полностью пропускаются во всех проходах. Добавляйте сюда операционные каталоги, которые не нужны в отчёте.

---

### `aDocTypeCodes` — белый список динамических каталогов
```javascript
var aDocTypeCodes = [
    // "my_doc_type_code",
];
```
Коды записей из каталога `doc_types`. Каждый код является именем динамического каталога, порождённого этим типом документа. Если массив пуст — проход 3 не выполняется.

Пример: если в системе есть `doc_type` с `code = "personnel_actions"`, добавьте `"personnel_actions"` в массив — и все записи этого каталога будут включены в отчёт.

---

### `aObjectDataTypeCodeFilter` — исключение типов `object_datas`
```javascript
var aObjectDataTypeCodeFilter = [
    "integration_systems",
    "fcache",
    // ...
];
```
Коды типов из каталога `object_data_types`. Записи `object_datas`, у которых `object_data_type_id` ссылается на тип с таким кодом, **исключаются** из отчёта. Если массив пуст — все `object_datas` обрабатываются без фильтрации по типу.

Используется для отсева служебных или интеграционных данных объектов.

---

### `aModLoginExclude` — исключённые логины
```javascript
var aModLoginExclude = [
    "admin",
    "user1",
    // ...
];
```
Если `modification_login` объекта совпадает с любым логином из этого массива — объект пропускается.

**Исключение:** для `override_web_templates` с непустым полем `mode` этот фильтр **не применяется** (см. ниже).

---

## Специальная логика для отдельных каталогов

### `override_web_templates`
Записи фильтруются по полю `mode`:

| Значение `mode` | Поведение |
|---|---|
| Пустое | Применяются все стандартные фильтры (дата, логин) |
| Непустое, совпадает с `code` одного из `web_modes` в отчёте | Запись включается **без проверки даты и логина** |
| Непустое, не совпадает ни с одним `web_modes` в отчёте | Запись **пропускается** |

Смысл: шаблоны переопределений, привязанные к режиму портала, включаются автоматически вместе с самим режимом.

### `object_datas`
Фильтрация через `aObjectDataTypeCodeFilter` (описано выше).

---

## Лог выполнения

Лог пишется в журнал с именем `report_non_std_objects`. В нём отображаются:
- Количество каталогов в каждом проходе
- Найденные ID типов для фильтров
- Ошибки XQuery по отдельным каталогам
- Итоговое количество строк в отчёте

Просмотр лога: **Администрирование → Журналы событий → `report_non_std_objects`**.

---

## Порядок первого запуска

1. Установить `sMinModDate` — дату, начиная с которой смотрим изменения.
2. Заполнить `aCatExclude` каталогами, которые не нужны.
3. Заполнить `aObjectDataTypeCodeFilter` кодами служебных типов `object_datas`.
4. При необходимости заполнить `aDocTypeCodes` кодами нужных динамических каталогов.
5. Установить `bGenerateColumns = true`, запустить отчёт — столбцы создадутся.
6. Вернуть `bGenerateColumns = false`.
7. Запускать отчёт повторно по мере необходимости.
