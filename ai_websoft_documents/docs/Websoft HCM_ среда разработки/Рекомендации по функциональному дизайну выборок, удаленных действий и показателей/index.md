## Рекомендации по функциональному дизайну выборок, удаленных действий и показателей

## **I.                   Цель документа**

Описание best practices, настоятельно рекомендованных к использованию при создании кода объектов API (выборок, показателей и удаленных действий).

## **II.                Общие рекомендации**

1.  Все карточки объектов API должны входить в категорию «Library» соответствующих справочников. Могут в какие-то еще, но в эту - обязательно
2.  Код должен быть разделен на две части:
    *   часть, остающуюся в объекте API (файле выборки, УД, показателя)
    *   часть, находящуюся в соответствующей библиотеке кода.

*   В объекте остается та часть алгоритма, в которой подготавливаются данные для выполнения требуемого функционала.

****Пример:****

iPersonID = OptInt( iPersonID, OptInt(sPersonID) );
if( iPersonID == undefined )
{
if( curObject != null && curObject.Name == "collaborator" )
{
iPersonID = curObjectID;
}
else
{
iPersonID = curUserID;
}
}
var arrStatuses = tools\_web.parse\_multiple\_parameter(sStatus);

*   В библиотеке кода реализуется та часть алгоритма, которая отвечает собственно за выполнение требуемого функционала.
*   Также в объекте реализуется обработка «всплывающих» из функции прерываний (throw) и ошибок.
*   Конкретика – в отдельных рекомендациях.

3.  Ошибки выводятся прерываниями (throw). Ошибки должны всегда выводиться как минимум в лог. По возможности - в интерактив. Обработчик этих прерываний и прочих ошибок – в файле объекта API.
4.  «Опорные» параметры ID в объектах API задаются всегда парой -   типа «ссылка на объект в базе» (для выбора объекта в Редакторе интерфейсов) и типа строка (для использования подстановок).
5.  При получении значения «опорного» ID из curObject/curObjectID необходимо проверять тип объекта на соответствие ожидаемому типу опорного объекта.
6.  Разное:
    1.  ParseJson try-catch’ить в обязательном порядке. OptParseJson пока не реализован …
    2.  При формировании строки XQuery запроса:
        1.  Логические операторы обрамлять пробелами. Особенности парсера XQuery: в ряде случаев возникает ошибка парсера при слитном написании строки с логическими операторами.
        2.  Исключить лишние, необязательные пробелы. Особенно, при запросе по $elem\_qc, поскольку в этом случае не выполняется оптимизация запроса.

## **III.            Как определить какая часть кода должна располагаться в библиотеке?**  
**И как его оформить**

1.  Код, оформленный как функция библиотеки, потенциально должен быть доступен для вызова как web-сервис (oAPI). Функции библиотек кода могут быть вызваны из произвольного, заранее неизвестного интерфейса на клиенте (react, angular, vanilla JS, исполняемое приложение ОС, в т.ч. мобильное)
2.  Алгоритмически в нем должен находиться функционал, который, собственно, реализует описанную в тикете задачу. Включая проверки аргументов функции на корректность, но исключая подготовку данных, зависящую от среды выполнения и пр.
3.  Интерфейсную часть удаленных действий (формирования и обработку возврата экранных форм УД) также нужно располагать в файле УД, а не в библиотеке.
4.  Считаем, что все данные, необходимые для срабатывания функции на момент её выполнения уже известны.

## **IV.            Отдельные рекомендации**

### Рекомендации по выборкам

1.  Разделение кода: в файле выборки остается функционал, проверяющий входящие параметры и преобразующий их тип к исходному смыслу параметра для передачи в функцию. Например, собирание «опорного» ID из параметров выборки, curObject и curUser. Или преобразования JSON в реальный объект или массив
2.  Файлы выборок располагаются в /wtv/remote\_collections

### Рекомендации по показателям

1.  Разделение кода: аналогично выборкам
2.  Файлы показателей располагаются в /wtv/statistics

### Рекомендации по удаленным действиям

1.  Разделение кода: в файле удаленного действия реализуется подготовка входных параметров и вся интерфейсная часть алгоритма – обработка режима (command) удаленного действия, формирование экранной формы, получение возврата из экранной формы. В функцию библиотеки кода выносятся только непосредственно те преобразования данных, которые являются сутью удаленного действия.
2.  Файлы удаленных действий располагаются в /wtv/remote\_actions

## **V.               Окружения (среды) запуска объектов API**

Есть три (актуальных) окружения, в котором запускаются объекты API:

*   Runtime LPE (Редактор интерфейсов)
*   Мобильное приложение
*   Админка

Основная особенность заключается в том, что в настоящее время наличие и заполненность глобальных (по отношению к коду объекта API) переменных, содержащих «опорный» объект (или их набор) а также прочих переменных, за исключением разве что curUser в окружениях отличаются.

Также есть отличия в интерпретаторах УД.

### **Показатели**

Runtime LPE:

1.  В окружении показатель срабатывает при открытии соотв. страницы.
2.  Параметры показателя можно переопределить в типе страницы, в которой показатель прописан для использования.
3.  Подстановки для показателя в окружении не используются за отсутствием смысла в них для показателя.
4.  Показатель может возвращать скалярное значение (тип возврата – real), строковое представление скалярного значения или JSON с объектом
5.  В окружении инициализированы все глобальные переменные, существующие в контексте портала:

*   curUser/curUserID
*   curObject/curObjectID
*   curWebDesign/curWebDesignID
*   curSite/curSiteID
*   curLng/curLngWeb/curLngID

Мобильное приложение:

В настоящее время показатели в мобильном приложении не используются

Админка:

В настоящее время показатели в Админке не используются…

###   **Выборки**

Runtime LPE:

6.  В окружении выборка срабатывает в зависимости от настроек или   при открытии соотв. страницы или при открытии виджета с выборкой/таба с виджетом..
7.  В окружении существует механизм подстановок , позволяющий передавать средствами рантайма значения полей между используемыми в «сборке» LPE объектами API. Например, вычисленный в показателе «опорный» ID во входные параметры выборок и удаленных действий.
8.  В окружении инициализированы все глобальные переменные, существующие в контексте портала:

*   curUser/curUserID
*   curObject/curObjectID
*   curWebDesign/curWebDesignID
*   curSite/curSiteID
*   curLng/curLngWeb/curLngID

Мобильное приложение:

1.  В окружении выборка срабатывает при открытии соотв. пункта в мобильном приложении.
2.  Вызов выборок – внеконтекстный, curObject/curObjectID отсутствует.
3.  Инициализация в окружении глобальных переменных:

*   curUser/curUserID – **определено и заполнено**
*   curObject/curObjectID – **не определено**
*   curWebDesign/curWebDesignID – **определено и заполнено**
*   curSite/curSiteID – **определено и заполнено**
*   curLng – **определено и заполнено**
*   curLngWeb – **определено и заполнено**
*   curLngID – **определено и заполнено**

  Админка:

1.  Инициализация в окружении глобальных переменных:

*   curUser/curUserID – **определено и заполнено**
*   curObject/curObjectID – **определено и пусто**
*   curWebDesign/curWebDesignID – **не определено**
*   curSite/curSiteID – **не определено**
*   curLng – **не определено**
*   curLngWeb – **определено и пусто**
*   curLngID – **определено и пусто**

### **Удаленные действия**

Runtime LPE:

1.  В окружении инициализированы все глобальные переменные, существующие в контексте портала:

*   curUser/curUserID
*   curObject/curObjectID
*   curWebDesign/curWebDesignID
*   curSite/curSiteID
*   curLng/curLngWeb/curLngID

2.  В окружении существует механизм подстановок , (см. выборки )
3.  Для передачи подстановкой в удаленное действие текущей , контекстной записи (на которой было вызвано УД) применяется шаблон подстановки _{{ITEM}}_ . Для передачи в УД определенного поля этой записи используется конструкция _{{ITEM.fieldname}}_ . Например _{{ITEM.id}}_ .

Мобильное приложение:

1.  Инициализация в окружении глобальных переменных:

*   curUser/curUserID – **определено и заполнено**
*   curObject/curObjectID – **определено и пусто**
*   curWebDesign/curWebDesignID – **определено и заполнено**
*   curSite/curSiteID – **определено и заполнено**
*   curLng – **определено и заполнено**
*   curLngWeb – **определено и заполнено**
*   curLngID – **определено и заполнено**

2.    «Опорный» объект передается посредством специфического для МП механизма переопределения WVARS удаленного действия. Поэтому в УД обязательно должны быть параметры для передачи «опорного» объекта.
3.  Открытие ссылок из УД в мобильном приложении:
    1.  Команда redirect из УД в мобильном приложении открывает переданную ссылку в системном компоненте WebView. Который не является полнофункциональным браузером и кое-что в нем может не работать (например в нем не работает веб-класс). Зато в него прозрачным образом передается текущая аутентификация пользователя МП.
    2.  Для открытия в отдельном процессе в стороннем браузере необходимо использовать команду new\_window _._ Но при этом потребуется отдельно аутентификация на портале в открывшемся окне.

Админка:

2.  Инициализация в окружении глобальных переменных:

*   curUser/curUserID – **определено и заполнено**
*   curObject/curObjectID – **определено и пусто**
*   curWebDesign/curWebDesignID – **не определено**
*   curSite/curSiteID – **не определено**
*   curLng – **не определено**
*   curLngWeb – **определено и пусто**
*   curLngID – **определено и пусто**

3.  В окружении в УД может передаваться ID «опорного» объекта или коллекция ID «опорных» объектов. Для этого используются специфические для окружения глобальные (относительно кода УД) переменные:
    1.  OBJECT\_ID – для передачи единичного ID «опорного» объекта
    2.  SELECTED\_OBJECT\_IDS – для передачи коллекции ID. Коллекция передается как строка из ID, разделенных «;». Для преобразования в массив можно использовать tools\_web.parse\_multiple\_parameter() или .split(‘;’) с дальнейшим преобразованием   массива строк с массив bigint
    3.  ELEMENT\_IDS – список дополнительных идентификаторов. Используется при вызове действия внутри объектов, содержащих вложенные структуры/массивы. При таком вызове возникает интерфейсная возможность вызвать действие для конкретной строки такого вложенного массива – в атрибуте OBJECT\_ID придет идентификатор, например, мероприятия, а в ELEMENT\_IDS, например – идентификаторы преподавателей, выделенных в списке.
